# 通しドキュメントを現状に合わせる

`docs/` には2種類のドキュメントがある。

- **日付つき**（`docs/2026-*.md`）— その日の測定の手順と生の数字。**書いたら以後は直さない**（記録なので）
- **通し**（`progress-log.md` / `related-work.md` / `README.md` / `docs/README.md`）
  — 常に「いまの状態」を表す。**このスキルが直すのはこの4本だけ**

## 編集しないもの

- **`docs/PRD.md`** — **要件定義はユーザーが自分の手で書く文書。このスキルからは編集しない。**
  古くなっていても、他のファイルから参照している節が無くなっていても、**直さずに指摘だけする。**
  直し方の案を添えるのはよいが、実行はユーザーの判断を待つ
- **`dialogs/`** — 議事録なので絶対に編集しない
- **`docs/2026-*.md`** — その日の記録なので、書いたあとは直さない

**PRD が変わったときに周辺を追随させるのは、このスキルの仕事である。**
`docs/README.md` の索引・`scripts/check_docs.py` の記号検査・コード中の参照を
現状に合わせる作業は行ってよい。触ってはいけないのは PRD 本体だけ。

## いちばん大事な原則 — 同じことを2箇所に書かない

ドキュメントが読みにくくなる原因は分量ではなく、**同じ情報が複数の場所にあること**である。
測定値が PRD と progress-log の両方にあると、片方だけ古くなって
「どちらが本当か」が読み手に判定できなくなる。

| 情報 | 主に書く場所 | 他のファイルでは |
|---|---|---|
| 測定値・経緯 | `progress-log.md` | 数字を再掲するなら測定条件を添える |
| P / S / R の定義と達成状況 | `docs/README.md` | 他のファイルは番号を使うだけ |
| 論文の中身 | `related-work.md` | `PRD.md` は参照するだけ |
| 使い方・API | 直下の `README.md` | `docs/` はリンクで済ませる |

**判断に迷ったら「この情報は他のファイルにもあるか」を先に確かめる。**
あるなら、書くのではなく参照する。

### PRD が現状と食い違っていたら

**直さない。報告する。**次の形で伝えて、判断を待つ。

1. どこが食い違っているか（行番号と、いまの記述）
2. なぜそう言えるか（`results/` の値や実装との差）
3. 直すならこうなる、という案

2026-09-01 に、構造上の問題を見つけて 733行から426行に書き直したことがあるが、
**「LLM が読むことを前提に書かれた文章になっていて人間が読めない」として差し戻された。**
最終的にユーザー自身の手で 153行に書き直されている。
経緯と、何が悪かったのかの実測は `docs/2026-09-01-docs-review.md` にある。

## 手順

### 1. 何が動いたかを機械的に集める

推測で書かない。まず差分を取る。

```bash
python3 scripts/check_docs.py          # 機械的に見つかるズレの一覧
git log --oneline -20 --name-only      # 何を触ったか
git status --porcelain                 # 未コミットの作業
```

`check_docs.py` は本数・索引漏れ・記号（P/S/R）の不整合と、
「通しドキュメントを最後に直してから素材だけが動いたコミット」を出す。
**内容の正しさは見ていない**ので、ここが通っても更新済みの証明にはならない。

数字を扱うときの正本は `results/leaderboard.csv`（シエンタ）と
`results/leaderboard_vehicles.csv`（Craigslist）。本文の数字はここから引く。

### 2. 4本を、それぞれの役割の範囲でだけ直す

| ファイル | 何を書くか | 何を書かないか |
|---|---|---|
| `docs/progress-log.md` | 第1部にその日の箇条書きを追記。数字が動いたら第2部の該当する表を直す。**完了報告はここ** | 手順の詳細（日付つきドキュメント側に書く） |
| `docs/related-work.md` | 新しく読んだ論文。R 番号は**追記のみ**で、既存の番号を振り直さない | 測定結果（progress-log の担当） |
| `README.md`（直下） | インストール・使い方・API の例。`unfold/` の公開 API が変わったときだけ | 測定値の一覧（`docs/` へのリンクで済ませる） |
| `docs/README.md` | 日付つきドキュメントを足したら索引の表に1行足し、冒頭の「NN本」を直す。**P / S の判定はここで直す** | 説明の本体（各ドキュメントの担当） |

`docs/PRD.md` はこの表に無い。**編集対象ではない**ので、直したくなったら報告に回す。

**P / S / R の定義と達成状況は `docs/README.md` にある。**2026-09-01 の書き換えで
PRD から P / S / R の表が無くなったため、判定を直すのはこのファイル1箇所でよい。
`scripts/check_docs.py` も docs/README.md を定義元として見ている。

### 3. 数字を書くときの決まり

- **単位を混ぜない。** シエンタは万円、Craigslist は USD。2つのデータセットの数字を並べない
- **実行環境をまたいだ数字を同じ表に並べない。** `leaderboard*.csv` の `実行環境` 列
  （`mac` / `node`）が違う行は、LightGBM のバイナリ差で 0.08% ほどズレる
- **リーク済みの値を実測として書かない。** `*_LEAKED*.csv` と、
  8/31 までの Craigslist の測定（中間 parquet の並び順が固定される前のもの）は再現できない
- **良すぎる結果は疑う。**（過去にリークを2件見つけている）。断定する前に部分集合で採点し直す

### 4. 書き方

- **日本語で書く。** 英語化はしない（2026-09-01 に「一旦保留」で決着している）
- 既存の節の文体・粒度に合わせる。表は表のまま、箇条書きは箇条書きのまま足す
- 撤回・訂正は消さずに残す。「前日の一般則は複数車種では再現しなかったので撤回した」の形

### 読める形を保つための書式の決まり

**表のセルに段落を書かない。** 1セルは1文まで。長くなったら表の下の本文に出す。
（旧 PRD の検証計画で1セルが 578桁になり、表として機能しなくなった実例がある）

**数字には条件を添える。** `2,580.78` ではなく `2,580.78（6万行・5-fold）`。
同じ指標の値が行数や測定日で変わるので、条件がないとどれが現行か分からない。
複数の値が併存するなら、片方を消すのではなく**両方に条件を書く**。

**1行は概ね100桁（全角50字）以内で折る。** 差分が読めなくなる。

**表と記号で置き換えない。** 説明を表のセルに畳んだり、新しい記号
（`P` / `S` / `R` 以外）を作って参照で繋いだりすると、検索はしやすくなるが
**人間が通読できなくなる。**2026-09-01 にこれをやって差し戻している。
理由が要る話は、表の1行ではなく地の文で書く。

### 5. 検算する

```bash
python3 scripts/check_docs.py
```

指摘が消えていることを確認する。消せない指摘（書式を意図的に変えた等）があるなら、
その理由を報告に添える。最後に、**何をどう直したかを1〜2文で要約して伝える**。

## 関連するしくみ

`git commit` の直前に `.claude/hooks/check_docs_updated.py` が走り、
`results/` や `unfold/` だけをコミットしようとして通しドキュメントが1本も入っていないときに
確認を求める。**拒否ではない**ので、記録を後でまとめる進め方はそのまま通せる。
