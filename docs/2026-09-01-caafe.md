# 機能A と CAAFE を同じ土俵で比べた（S4）

2026-09-01 / `scripts/caafe.py`・`scripts/run_caafe.py` / 実費 $1.20

## 何を確かめたかったか

**唯一残っていた未測定の受け入れ基準（S4）を埋める。**

非構造テキスト（Craigslist の `車種名`。出品者が自由に書いた文字列で 19,739 種類）を
どう扱うかについて、2つの設計が対立している。

| | CAAFE | 機能A（`unfold.Feature`） |
|---|---|---|
| LLM の仕事 | **前処理コードを書く** | 表記のゆれを吸収する（既定は埋め込み＋近傍） |
| 出力 | pandas のコード | 型のついた列 / 埋め込み列 |
| 予測時の LLM | 呼ばない（コードが残る） | 確信度の低い行だけ |
| 人が読めるもの | 生成されたコード | 来歴（`explain`） |

CAAFE は NeurIPS 2023 の手法（Hollmann et al. https://arxiv.org/abs/2305.03403）で、
14 データセット中 11 で改善したと報告されている。PRD §7-6 には
**「ここで負けたら機能A の実装方針をコード生成側に寄せる判断もありうる」**と書いた。

## 測り方

`docs/2026-08-29-feature-vehicles.md` と同じ土俵に乗せた。

- データ: Craigslist 60,000 行（seed 42）
- 分割: 5-fold・seed 42
- 下流モデル: LightGBM（同じハイパーパラメータ）
- 指標: MAE（平均絶対誤差。予測が平均で何ドルずれるか）

CAAFE 側は fold ごとに独立に作り直す。

1. その fold の train から 20,000 行を抜き、8:2 に割って内側の train / 検証にする
2. 列の様子とデータセットの説明を Claude に見せ、pandas のコードを提案させる
3. 実行して**検証 MAE が下がったコードだけ採用**する（本家と同じ採否基準）
4. これを 10 回くり返し、採用したコードを fold の train / test に当てて外側の MAE を測る

**test は生成に一切見せていない。** 本家との違いは下流モデル（本家は TabPFN + ROC AUC）と
LLM（本家は OpenAI、こちらは Claude）だけで、骨格は同じ。

**CAAFE に渡す列は他の手法と完全に揃えた。**特に `説明文` は渡していない。
平均 2,972 字あってプロンプトが桁で膨らむうえ、43.7% の行に売り値が書いてあるので、
そこから数字を拾うコードを書かれると予測ではなく答えの読み取りになるため
（`docs/2026-09-01-description-leak.md`）。

## 結果

| 手法 | MAE（USD） | 振れ幅 | 8/29 の測定 |
|---|---:|---:|---:|
| **F(c)' ＋機能A（埋め込み列）** | **2,580.78** | ±30.63 | 2,601 |
| B2' ＋車種名を手書きルールで正規化 | 2,758.03 | ±27.21 | 2,783 |
| **CAAFE ＋生成した特徴量** | **2,797.93** | ±110.50 | — |
| A2' 構造化列のみ | 3,229.94 | ±14.41 | 3,234 |

比較線2つが 8/29 の値をほぼ再現している（差は 20〜25 USD で、6万行の抽出が
変わったこと（`docs/2026-09-01-adaptive.md`）で説明がつく範囲）。
つまり以下はこの土俵の上で読める。

### 有意性（5-fold の対応のある t 検定）

| 比較 | 差 | p | fold ごとの勝敗 |
|---|---:|---:|---|
| 機能A − CAAFE | **−217.15** | **0.007** | **5/5 で機能A の勝ち** |
| 機能A − 手書きルール | −177.25 | 0.0001 | 5/5 |
| CAAFE − 手書きルール | +39.90 | 0.41 | 2/5（差なし） |

**S4 は満たした。** 機能A は CAAFE より 217 USD 良く、5 fold すべてで勝っている。
差は振れ幅（±30〜110）を超えている。

**CAAFE は手書きルールと同着だった。** LLM にコードを書かせても、
人が30分で書く正規化ルール（`normalize_model`: 区切り以降を捨てて先頭2語を取る）と
同じところに着地する。**どちらも「車種名を人間が読める単位に切り分ける」ことしか
していない**のに対し、埋め込みは切り分けずに連続量として持つので、
「f-150 lariat」と「f150 xlt」が近いことを表現できる。ここが 217 USD の差になった。

CAAFE が何もしないよりは良い（3,230 → 2,798、13% 改善）ことは付け加えておく。
**構造化列しかない状況で自由記述を活かす手としては有効**である。

## 途中で見つかったこと: 生成コードは「状態」を持つ

**最初の測定で CAAFE は 3,329 と、何もしない 3,230 より悪かった。**
採用条件が「検証 MAE が下がったコードだけ」なので、原理的に起きないはずである。

原因は生成コードに混ざるこういう処理だった。

```python
df['base_model_code'] = pd.factorize(key)[0]         # 出現順に番号を振る
df['model_key_freq']  = key.map(key.value_counts())  # そのフレーム内での頻度
df['mile_vs_model']   = mil - mil.groupby(key).transform('median')
```

`pd.factorize` は**渡されたフレームの中での出現順**に番号を振る。生成コードを
train と test に別々に当てると、同じ「f-150」が train では 3 番・test では 17 番になり、
**木が学習した分岐が test では別の車種を指す。**
実際、この種の列を採用した fold 3 と fold 5 だけ MAE が 3,550 / 3,492 に跳ねていた。

train と test をつないでから一度だけ当てる（`--apply-together`）と
**2,798 に戻り、5 fold すべてで改善した**（差 −531、p = 0.007）。
上の表はこちらの、CAAFE に有利な条件での値である。

これは CAAFE 方式そのものの弱点である。

- 生成されるのは「状態を持たない式」とは限らないのに、**適用は train / test 別々になる**
- 検証スコアは1つのフレームの中で測るので、**この不整合は検証時に見えない**
- つないでから当てれば直るが、それは **test の行を見て統計を取ること**（transductive）で、
  運用（明日入ってくる1台を査定する）では成立しない

**機能A にこの問題は無い。**`fit` で train の状態を持ち、`transform` が test に
同じ変換を当てる scikit-learn の約束を守っているためで、
これは実装の細部ではなく**設計の差**である。

## この結果をどう使うか

- **機能A の設計方針は維持する。** PRD §7-6 の「負けたらコード生成側に寄せる」は発動しない
- ただし **CAAFE の出力（コード）が読めるという利点は本物**である。機能A の埋め込み列は
  384 次元の数字で、なぜその予測になったかは `explain()` の来歴でしか辿れない。
  「人がレビューして本番に置ける前処理が欲しい」という要求には CAAFE のほうが向く
- **併用は試していない。** 埋め込み列 ＋ CAAFE の生成列を両方入れると
  さらに下がる可能性がある（今回はどちらか一方でしか測っていない）

## 再現

```bash
.venv/bin/python scripts/run_caafe.py --n-iterations 10 --apply-together   # 本番
.venv/bin/python scripts/run_caafe.py --skip-caafe                          # 比較線だけ（無料）
```

`results/caafe.csv`（別々に当てた版）・`results/caafe_together.csv`（つないで当てた版）・
`results/caafe_steps*.csv`（提案の全記録。却下されたものも残してある）。
