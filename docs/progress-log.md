# 進捗ログ — 経緯と結果

**目的**: 「いつ・何をして・何がわかったか」の時系列（第1部）と、
測定結果の主題別まとめ（第2部）を1枚にまとめる。
個別の測定の手順と生の数字は各日の `docs/2026-*.md` にあるので、ここは索引を兼ねる。
要件と設計判断は `docs/PRD.md` を見る。

**読み方**: 主指標は **MAE（平均絶対誤差）**。予測が平均でいくらズレるかを、
値段そのものの単位で表したもの。**小さいほど良い。** シエンタは万円、
Craigslist は USD で測っている。単位が違うので、2つのデータセットの数字を
直接比べてはいけない。**p 値**は「差がまぐれで出る確率」。0.05 未満なら偶然とは
考えにくい、というのが通例。**fold** は交差検証でデータを分けた組で、5-fold なら
5通りの分け方すべてで測る。「5/5 fold で勝ち」は全通りで勝ったという意味。

**運用**: 作業が一段落するたびに第1部のその日の欄に箇条書きを足す。
数字が動いたら第2部の該当する表も直す。

**このファイルの由来**: 2026-09-01 まで時系列（`progress-log.md`）と
主題別（`results-summary.md`）の2本に分かれていたが、同じ測定値が両方に載って
二重管理になっていたため、同日に本ファイルへ統合した。

# 第2部 — 結果（主題別）

## 1. 一言でいうと

**テキストに本当に情報がある場所では、LLM を挟むと既存の最良手法を上回る。
情報が無い場所では上回らない。** 中古車価格予測を題材に、それを同じ物差しで測り切った。

成果物は scikit-learn 互換のライブラリ `unfold` で、設計書の3本柱
（機能A・機能B・信頼度ルーティング）がすべて API になっている。

## 2. 受け入れ基準の達成状況

作る前に決めた合格ラインに対する現在地。基準の定義は `docs/README.md` §2。

| | 基準 | 結果 | 判定 |
|---|---|---|---|
| S1 | 機能A が比較線を有意に下回る | 2,580.78 対 2,586.88（差 −6.10、振れ幅 ±32 以内） | **同着** |
| S2 | 機能A が未知 model で文字TF-IDF に勝つ | 3,637.05 対 3,622.03（+15.03） | **未達** |
| S3 | 機能A が人手ルールに負けない | 2,580.78 対 2,758.03（−177.25 USD・6万行・5-fold） | **達成** |
| S4 | 機能A が CAAFE に勝つ | 2,581 対 2,798（Craigslist・p=0.007、5/5 fold） | **達成** |
| S5 | TabPFN に勝つ | 12.21 対 12.95（シエンタ 5,507行） | **達成** |
| S6 | 機能B が最良の単体モデルを有意に下回る | 1,980.68 対 2,591.58（p=0.016、5/5 fold） | **達成** |
| S7 | コストを提示できる | 機能B $0.0086〜0.0121/行、機能A フォールバック $0.0016〜0.0053/行 | **達成** |
| S8 | 来歴を辿れる | `explain` / `confidence` / `examples` / `cost` / `provenance` | **達成** |

**8項目中6つ達成、1つ同着、1つ未達。** 未達の S2 は、機能A の単一表現が
未知の model では文字 TF-IDF にわずかに及ばないというもの。ただし
**併用すれば未知 3,620.23 で同着になり、全体は最良 2,577.03** になるので、
使い方の指針が1つ増えたと読むのが正しい。

## 3. データセットごとの到達点

## 4. 機能ごとの結果

どの機能を、何と比べて判定したかを先に置く。数字は各項と §3 にある。

| 機能 | 比べた相手 | 基準 | 測ったデータ |
|---|---|---|---|
| 機能A | 人手ルール（シエンタ Ab1 / Craigslist B2） | S3 | 両方 |
| 機能A | 文字TF-IDF（C2）・e5 埋め込み（D1・D4） | S1・S2 | 判定は Craigslist |
| 機能A | CAAFE（R2・LLM にコードを書かせる側） | S4 | Craigslist のみ |
| 機能A の LLM フォールバック | 呼ばなかった場合（0%）の自分自身 | — | 両方 |
| 機能B | LightGBM ＋ 文字TF-IDF（最良の単体モデル） | S6 | 両方 |
| 器の比較 | TabPFN（R6・LLM を使わない側の到達点） | S5 | シエンタのみ |

### 機能A（`Feature`）— 非構造列を型付き列にする

**人手ルールと同じところに、半分の手数で着地する。**
手書きの正規表現を書かず、追加依存のない既定エンコーダ1本（文字 n-gram TF-IDF + SVD256）で
D4（埋め込みと文字TF-IDF の併用）と同着になる。

仕様書の前提を1つ覆した。**教師ラベルは「値の名前だけ・ラベル0件」が最も良く、
人手ラベル200件より 2.31 万円良い**（`docs/2026-08-29-feature-skeleton.md`）。
ラベル作成という工程は要らなかった。

**LLM フォールバック（設計書05）**: 確信度の低い15%だけ LLM に回すと、
**宣言した10グレードに該当する行の正解率が 0.873 → 0.942**。**回した行は全問正解**だった
（`docs/2026-09-01-feature-fallback.md`）。「迷った行だけ LLM」という設計が裏付けられた。

正解率は2つある。**全体**は宣言値の外の行（どう答えても不正解になる行）を含み、
**宣言値内**はそれを除いた母数で測る。上の 0.873 → 0.942 は後者である。
いずれもシエンタ・fold1 の test 400行での値。

| エスカレーション率 | 全体の正解率 | 宣言値内の正解率 | 費用 |
|---:|---:|---:|---:|
| 0%（LLM なし） | 0.790 | 0.873 | $0 |
| 5% | 0.833 | 0.920 | $0.106 |
| 15% | 0.853 | 0.942 | $0.215 |
| 30% | 0.885 | 0.978 | $0.333 |

**「回した行は全問正解」も宣言値内での話である。** 予測は宣言した10値の
どれかにしかならないので、正解した行は必ず宣言値内に入る。30% 回したときの
120行のうち、宣言値の外にあった19行は分母から外れている
（`results/feature_fallback.csv`）。

**Craigslist でも成り立った（9/2）。** ただし同じ形（正解＝人手ルールの結果）で
移植した1度目は、正解が入力の部分文字列になり 0% の時点で頭打ちになって成立しなかった。
正解をデータ自身が持つ `type`（ボディ形状・13水準）に替えて測り直した
（`docs/2026-09-02-feature-fallback-vehicles.md`）。

入力は `model`（自由記述）、宣言値は type の13水準でカバー率 100%。
Craigslist・fold1 の test 400行、教師ラベルは人手200件、エンコーダは既定の文字TF-IDF。
**上限 0.822 / 下限 0.278** の課題である（下記）。

| エスカレーション率 | 正解率 | 回した行の正解率 | 費用 |
|---:|---:|---:|---:|
| 0%（LLM なし） | 0.537 | — | $0 |
| 5% | 0.562 | 0.750 | $0.101 |
| 15% | 0.620 | 0.817 | $0.190 |
| 30% | 0.637 | 0.700 | $0.217 |

**上限は「同じ入力テキストの多数決」。** `type` は出品者が各出品で選ぶ値なので、
`f-150` が truck 471件 / pickup 450件 のように割れている。入力テキストだけを見る
手法はこれを超えられず、採点した400行では 0.822 になる。下限は最頻クラス
（`sedan`）を常に答える 0.278。**LLM の誤り36件のうち18件は pickup↔truck の
入れ替わり**で、この揺れを除けば回した行の正解率は 0.850 に相当する。

**シエンタと違い、値の名前だけ（ラベル0件）は起点にならなかった。** 0% で
0.142〜0.233 と下限を下回る。`model` と `pickup` のように**入力と値の名前が
語彙を共有しない課題**では、近傍分類が手がかりを持てないため。
e5 埋め込みに替えても 0% は文字TF-IDF とほぼ同じ（0.530 対 0.537）で、
LLM を足すと逆に伸びが小さい（15% で +0.055 対 +0.083）。
**埋め込みが良いほどルーティングが良くなるとは限らない。**

### 機能B（`LLMPredictor`）— 統計モデルの上に乗る最終判断

**複数車種では合格、単一車種では不合格。**

| | 機能B | 比較線 | 差 |
|---|---:|---:|---:|
| Craigslist（600行） | **1,980.68** | 2,591.58 | **−23.6%**（p=0.016、5/5 fold） |
| シエンタ（300行） | 12.85 | 12.99 | −1.1%（有意でない） |

差の理由ははっきりしている。**LLM の修正が当たる率**が、シエンタ 46%（コイン投げ）に対し
Craigslist 67%。**テキストに情報がない場所では LLM も効かない。**
事前スクリーニング（`unfold.screen()`）が、この見極めを測定前に行う道具にあたる。

| データ | 列 | テキスト寄与率 | 判定 |
|---|---|---:|---|
| シエンタ | 装備テキスト | 4.3% | 効きにくい |
| Craigslist | model | **15.4%** | 試す価値あり |
| Craigslist | description | 3.7% | 効きにくい |

### 信頼度ルーティング（`AdaptivePredictor`）— 全行を LLM に投げない

6万行に機能B を素で当てると **$516・17時間**かかるため、絞る仕組みは必須だった。
最も良い信号は「**LightGBM と XGBoost の食い違い**」＝統計モデル自身が迷っている行。

| LLM に回す割合 | MAE | 費用 | 推定時間 |
|---:|---:|---:|---:|
| 0% | 3,042.6 | $0 | 24 秒 |
| 10% | 2,907.3 | $0.52 | 61 秒 |
| 30% | 2,673.5 | $1.57 | 130 秒 |
| 50% | 2,581.1 | $2.62 | 199 秒 |
| 100% | 2,265.5 | $5.23 | 369 秒 |

**精度は割合に対してほぼ線形に効き、費用も線形。**
どこで止めるかは予算で決められる、という形になった。

## 5. 費用とレイテンシ（応答時間）

| 項目 | 実測 |
|---|---|
| 機能B 1行あたり | $0.0086〜0.0121 |
| 機能A フォールバック 1行あたり | $0.0028〜0.0053（シエンタ 400行）/ $0.0016〜0.0050（Craigslist 400行） |
| LLM 1件の応答時間（中央値） | 4.6 秒 |
| 統計モデルだけの応答 | 6 ミリ秒 |
| 統計モデルの fit + 近傍索引の構築 | 23.9 秒 |

**1件あたりの応答時間は並列数を上げても縮まない**（API 側の素の速度）。
一方**全体時間は並列数にほぼ反比例し、費用は並列数を変えても同じ**。

| 並列数 | 全体（15行） | 1行あたり |
|---:|---:|---:|
| 1 | 88.6 秒 | 5.91 秒 |
| 4 | 23.9 秒 | 1.60 秒 |
| 8 | 15.5 秒 | 1.03 秒 |

**バッチ処理なら問題ないが、対話的な用途（1台を画面で査定する）では 4.6 秒は長い。**
ここで信頼度ルーティングが効く。

## 6. 見つけた落とし穴

測定を良く見せてしまう罠を2件見つけ、どちらも**部分集合に分けて採点する**ことで検出した。

**1. 同一車の重複出稿（42%）。** 同じ VIN が最大 261 件あり価格まで同一。
放置してランダム分割の交差検証をすると、同じ車が train と test の両方に入る。
MAE が 4.2%・R² が 0.03 だけ良く見える。→ 1台1行に潰す処理を入れ、
検知自体を `unfold/leakage.py` としてライブラリの責務にした。

**2. description に価格が書かれていた。** 自由記述を渡したら 40% 改善したので疑ったところ、
採点した600行のうち **262行（43.7%）の description に価格そのものが書かれていた**。

| 構成 | 全600行 | 価格記載あり(262) | 記載なし(338) |
|---|---:|---:|---:|
| description なし | 2,335.32 | 2,035.29 | 2,567.89 |
| description あり・伏字なし【無効】 | 1,545.86 | 718.65 | 2,187.07 |
| **description あり・伏字あり** | **1,980.68** | 1,738.89 | 2,168.10 |

**価格記載のある行だけ 65% 改善**という偏りが動かぬ証拠になった。
→ `mask_amounts()` で既定で伏せる形にし、これもライブラリ側の責務にした。
出品・求人・不動産など、自由記述に答えが書かれるデータでは常に起きるため。

**伏せて測り直しても 23.6% の改善が残り、効果は本物**だと確認できている。

### 撤回した結論が1件

前日に立てた「**弱い証拠は LLM を汚染する**」という一般則は、複数車種では
再現せず符号も逆だった。**シエンタ固有の現象**であり、一般則ではなかったので撤回した。

### 実施不能と判定した項目が1件

画像モダリティ（P5）は、着手前に15分で画像URLの生存確認をしたところ
**100件中100件が 404** だった。半日〜1日の無駄を回避できた。

## 7. 実行環境

**測定は計算ノード（Ubuntu 24.04 / 16 vCPU / 64GB）で行う。**
2026-09-01 に手元の Mac から移行した（`docs/2026-09-01-migration.md`）。

移行の決め手は CPU の速さではなく、**17時間のジョブをノートPCで走らせられない**こと。
実測の速度差は 1.5〜2.2 倍で、事前の見積もり（3〜5倍）には届かなかった。

**注意: 機械をまたぐと値が僅かにズレる。** 同じ 60,000行・5-fold を両環境で回すと、
A2（13列）は完全一致するが、C2（1,013列）は 2,616.96 対 2,619.04 で 2.08 ずれる。
データ・スレッド数・TF-IDF 行列はすべて同一であることを確認済みで、
原因は LightGBM のバイナリ差（AVX2 対 AVX-512、clang 対 gcc）。
ズレは 0.079% で fold 間のばらつき（±22〜24）より1桁小さいが、
**機械をまたいだ数値を同じ表に並べてはいけない。**

そのため `results/leaderboard*.csv` には `実行環境` 列があり、
値は測定機を表す短い札（`mac` / `node`）になっている。

## 残っている宿題

**設計書の3本柱（機能A・機能B・信頼度ルーティング）はすべて API になり、
受け入れ基準は8項目中6つ達成・1つ同着・1つ未達**（一覧は第2部 §2）。
残っているのは次の10点。

- **S2（未知の model）が未達** — 機能A の単一表現が、未知の model では
  文字 TF-IDF にわずかに及ばない（3,637.05 対 3,622.03）。
  併用すれば同着になるので、既定を併用にするかが判断待ち
- **機能A の LLM フォールバックの下流 MAE が未測定** — 中間ラベルの正解率が
  上がることはシエンタと Craigslist の両方で確かめたが、生成した列を価格予測に
  足したときの効果は測っていない。訓練側の行も同率でエスカレーションする必要があり、
  費用の桁が変わる（`docs/2026-09-02-feature-fallback-vehicles.md`）
- **テストが実装側に偏っている** — `unfold/` には101件あるが、比較対象の
  `scripts/` には1件も無い。比較線の正しさは「再実行して既測と一致するか」だけで
  担保している
- **機能A の 05 に結合テストが無い** — `Feature` から実物の `ClaudeFallback` を
  通す経路がテストされていない（詳細は第1部 9/2）
- **先行事例との比較が片側のデータセットにしかない** — TabPFN（S5）はシエンタ、
  CAAFE（S4）は Craigslist でしか測っていない
- **特徴量のバージョン管理** — 来歴 API は動くが、
  **3ヶ月後に再実行して同じ数字が出ることは保証していない**。S8 の積み残し
- **leaderboard の残りの行をノードで測り直すか** — `実行環境` 列の追加と
  主要な行の再測定は済んでいるが、`leaderboard.csv` は 68行中 55行、
  `leaderboard_vehicles.csv` は 44行中 32行がまだ `mac` のまま
- **8/31 までの Craigslist の測定を測り直すか** — 中間 parquet の並び順を
  9/1 に固定したため、それ以前の数値はそのままでは再現できない（600行の測定で約 $5）
- **画像モダリティの扱い** — Craigslist の画像URLが全滅しており実施不能。
  API の設計だけ残す案が推奨
- **予測区間を出すか** — 点推定だけでなく幅で答えるか（先行研究 R5・R7 の論点）

## 通して言えること

- **効く条件つきで示せた。** テキストに本当に情報がある場所（複数車種）では
  既存の最良手法を上回り、飾りでしかない場所（単一車種）では上回らない。
  どちらも同じ物差しで測った
- **良すぎる結果は必ず疑う。** リークを2件（重複出稿・description の価格）見つけ、
  どちらも「部分集合に分けて採点する」ことで検出した
- **間違った一般化は撤回する。** アブレーションの結論を1件、実測に基づいて訂正した
- **着手前に前提を15分で確認する。** 画像URLの生存確認がこれにあたり、
  最大の作業項目を1つ、無駄になる前に落とせた
