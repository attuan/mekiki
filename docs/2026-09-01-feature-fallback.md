# 機能A の LLM フォールバック（設計書05）の実測

**日付**: 2026-09-01
**実装**: `unfold/fallback.py` の `ClaudeFallback`
**再現**: `.venv/bin/python scripts/run_feature_fallback.py --n-test 400`
**関連**: PRD §6.1（機能A）/ §6.3（信頼度ルーティング）/ §7-9

---

## 何を確かめたかったか

機能A は「埋め込み → 近傍で分類 → 確信度が閾値未満なら LLM へ」という造りになっている
（設計書の 01〜05）。8/29 の時点で 01〜04 までは APIキー無しで作れて測れており、
**05 だけが `QueueOnlyFallback`（答えずにレビュー待ちに積むだけ）の差し込み口**だった。

キーが来たので実物を差して、1つだけ問うた。

> **近傍分類が自信を持てなかった行を LLM に回すと、実際に正しくなるのか。1行いくらか。**

これが成り立たないなら、信頼度ルーティング（設計書の AdaptivePredictor、PRD §6.3）の
前提そのものが崩れる。「全行を LLM に投げず、確信度の低い行だけエスカレーションする」
という設計は、**確信度が低い行こそ LLM が直せる行である**ときにしか意味がないからである。

---

## 測り方

タイトル列からグレード名の列を作る課題。人手ラベルは使わず、
**値の名前だけを宣言する**（PRD §7-1 の案b）。

```python
Feature(source="タイトル", type="category",
        values=["G", "Z", "X", "G クエロ", ...],   # 10個宣言
        escalate_rate=0.15, fallback=ClaudeFallback())
```

`escalate_rate` は「確信度の低い順に何割を LLM に回すか」。
0% → 30% と上げながら、生成した列が正規表現版のグレード名とどれだけ一致するか
（**accuracy** = 正解率）を見る。fold1 のみ・test から 400 行を抽出して測った。

**「宣言値に限った accuracy」を主指標にする。** 宣言した10値は実データの 90.5% しか
カバーしていない（実際のグレードは 116 水準ある）。残り 9.5% はどう頑張っても
正解になりようがないので、LLM の効果を見るなら宣言値に含まれる行で見る必要がある。

---

## 結果 — **成立した。しかも回した行はほぼ全問正解**

| エスカレーション率 | 実際に回した行 | accuracy | **宣言値に限った accuracy** | 回した行の宣言値内 accuracy | 費用 |
|---|---|---|---|---|---|
| 0%（LLM を呼ばない） | 0 | 0.790 | 0.873 | — | $0 |
| 5% | 20 | 0.833 | **0.920**（+0.047） | **1.000** | $0.106 |
| 15% | 60 | 0.853 | **0.942**（+0.069） | **1.000** | $0.215 |
| 30% | 120 | 0.885 | **0.978**（+0.105） | **1.000** | $0.333 |

**LLM に回した行のうち、宣言値に含まれるものは1つ残らず正解だった**（どの率でも 1.000）。
つまり近傍分類が迷った行は、LLM にとっては簡単な行だった。

**費用は 1行あたり $0.0028〜$0.0053。** 率を上げるほど1行単価が下がるのは、
共通の `system` プロンプトが Claude 側のキャッシュに載るため。

### 読み方

- **確信度は「LLM に回すべき行」を正しく選べている。** ランダムに 30% 選んだのでは
  こうはならない。信頼度ルーティングの前提（PRD §6.3）は**この課題では成立している**。
- **全行を LLM に投げる必要はない。** 15% 回すだけで宣言値内 accuracy が
  0.873 → 0.942 に上がり、費用は 400 行で $0.215 に収まる。
  全行に投げれば 400 行で約 $2.1 かかるので、**10分の1の費用で改善の3分の2**を取れている。
- **「回した行の accuracy」が率を上げると下がる**（0.95 → 0.84）ように見えるが、
  これは宣言値の外にあるグレード（正解になりようがない行）が混ざってくるためで、
  宣言値内で見れば一貫して 1.000 である。

## 機能B との対比

同じ日に測った機能B（`docs/2026-09-01-llm-predictor.md`）は統計モデルに届かなかった。
**同じ LLM・同じ日・同じデータで、機能A のフォールバックは成功し、機能B は失敗した。**
この差は示唆的である。

| | 機能A のフォールバック | 機能B |
|---|---|---|
| LLM に投げる行 | 確信度の低い**15%だけ** | **全行** |
| 課題の型 | 分類（候補10個から選ぶ） | 回帰（連続値を当てる） |
| 正解の存在 | テキストに書いてある（読めば分かる） | テキストからは決まらない |
| 結果 | **回した行は全問正解** | 修正が半々の当たり外れ |
| 1行あたり | $0.0028〜$0.0053 | $0.0105 |

**LLM が強いのは「テキストに答えが書いてあるものを読み取る」課題**であって、
「複数の数値証拠を重み付けて連続値を出す」課題ではない、と読める。
これは PRD §3 の R1（LLM は補完として有効）とも整合する。

## 測っていないこと

- **下流の MAE は測っていない。** 生成した列を価格予測に足したときの効果を見るには、
  訓練側の 4,405 行も同じ率でエスカレーションする必要があり、費用の桁が変わる。
  中間ラベルの accuracy が上がっても下流の MAE が良くなるとは限らない
  （PRD §7-3 で、両者の順位が実際に入れ替わった例がある）ので、**ここは要確認**。
- **fold1 のみ・400 行**での測定である。
- **能動学習の後半は未検証。** `ClaudeFallback` は答えた内容をレビュー待ちキューに
  積む（設計書の "Everything the fallback answers is queued as a labeling candidate"）が、
  「承認すると次回は高速パスが広がる」ところまでは回していない。
