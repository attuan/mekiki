# ドキュメントの構造を調べ、書き直しを試して差し戻した

**日付**: 2026-09-01
**きっかけ**: `docs/` の md ファイルが見づらく、読んでも意味が分からなくなっている、という指摘。
**結論**: 構造上の問題は実在した。ただし**全面的な書き直しでは解けなかった**ので差し戻した。
PRD は 0.5 のまま据え置き、この記録だけを残す。

---

## 1. 何を測ったか

感覚ではなく数字で症状を出すために、`docs/` の全ファイルについて
行数・表示幅・強調の数・見出し構造を機械的に数えた。

| 症状 | 実測 |
|---|---|
| `PRD.md` の分量 | 733行 / 64KB（`docs/README.md` には「728行」とあり既にズレていた） |
| 100桁を超える行 | `PRD.md` に 68行。最長は §8 の表の1行で **578桁** |
| 太字 `**` | `PRD.md` に 297箇所（1行あたり 0.4個）。`progress-log.md` は 124箇所 |
| 「最良」を指す数字 | `2,596` / `2,601` / `2,580.78` / `2,444` が同一ファイル内に併存 |
| 【最新】マーカー | `PRD.md` に 6箇所（すべて別の節） |

## 2. 見つけた問題

### 2.1 表のセルが段落になっている

`PRD.md` §8 の検証計画は、1セルに段落が4つ入っている行がある（578桁）。
表は一覧して比較するための道具なので、セルが段落になった時点で表の利点が消え、
かつ本文より読みにくくなる。§3 の先行事例の表も同じで、
論文の要約・主張・実測・判定を1行に詰めて 524桁ある。

**これが「見づらい」の直接の原因。**

### 2.2 同じ指標に複数の数字が残り、どれが現行か書いていない

Craigslist の「最良 MAE」だけで4つの数字が本文に出てくる。

| 値 | 条件 | 出てくる場所 |
|---|---|---|
| 2,596 | 手組みの併用・6万行 | §2.2-c / §6.1 / §8 |
| 2,601 | 機能A 初回・6万行 | §2.2-i / §8 の P1 |
| 2,580.78 | 9/1 に引き直した機能A・6万行 | §4.2 の S1 / §8 の P0.5 |
| 2,444 | 全 200,374 行 | §2.2-k |

行数もデータも違うので**全部正しい**が、並んでいる場所に条件が書かれていない。
読み手は「機能A は 2,601 なのか 2,580.78 なのか」で止まる。

### 2.3 決着済みのものが未決のものと同じリストに並んでいる

- §7 未決事項: **9項目中5項目が取り消し線つきで決着済み。**実際に未決なのは
  3（評価指標）・7（分布を出すか）・8（画像）の3つ
- §9 リスク: **10項目中5項目が【後退】【解消】**

PRD の冒頭には「未決事項は §7 に集めてあるので、次回ミーティングはそこを見れば足りる」
と書いてある。**この約束が成立しなくなっている。**4項目を探すために75行を読む必要がある。

### 2.4 時点の表示が古い

見出しは `## 2. これまでの進捗（2026-08-29 時点）` のままで、
中身は (k) まで伸びて 8/30 の夜間バッチを含む。【最新】が6箇所あるのも同じ理由で、
追記のたびに付けて前のを外していないため、マーカーが時系列の手がかりにならない。

### 2.5 PRD と progress-log の守備範囲が重なっている

PRD §2.2 は (a)〜(k) の測定記録で、`progress-log.md` 第2部と同じ内容。
**PRD 733行のうち 352行（48%）が測定記録。**要件を読みに来た人が測定記録を読まされる。

### 2.6 更新ルールが追記オンリーになっている

`.claude/skills/update-docs/SKILL.md` に3つのルールが並んでいた。

- 「決めた要件を後から書き換えない。判断が変わったなら『変わった』と書き足す」
- 「撤回・訂正は消さずに残す」
- 「既存の節の文体・粒度に合わせる。表は表のまま」

記録としては正しいが、**3つ合わせると「表のセルに追記し続ける」以外の逃げ道がない。**
`git log` を見ると PRD.md は15回更新され、ほぼ毎回 insertions ≫ deletions だった。
2.1〜2.5 はすべてこの帰結である。

## 3. 試した書き直しと、なぜ差し戻したか

上記への対処として、PRD を 733行から 426行に書き直した。
測定記録を `progress-log.md` へ、決着した論点を新設の `docs/decisions.md` へ移し、
判定を `docs/README.md` に一本化する構成である。

**書式の指標は改善した。**

| | 旧 | 書き直し版 |
|---|---:|---:|
| 行数 | 733 | 426 |
| 太字 | 297箇所 | 95箇所 |
| 100桁超の行 | 68 | 30 |
| 最長行 | 578桁 | 165桁 |
| §7 の未決事項 | 9項目中4項目が現役 | 6項目すべて現役 |

**しかし人間が読めなくなったので差し戻した。** 何をしたかを数えると理由がはっきりする。

- 既存の `P` / `S` / `R` に加えて `E1〜E8`（実測の結論）・`D1〜D8`（決着した論点）・
  `C1〜C3`（訂正）という**記号体系を3つ新設し、計144箇所で使った**
- 各文書の冒頭に「この文書の役割」「何の正本か」という管理用の表を置き、
  「正本」という語を14回使った
- **本文（散文）が 365行から 184行に半減した**

つまり、構造を整理したつもりで、実際にやったのは**散文を表と記号に置き換えること**だった。
一番はっきり出ているのが次の例である。

**旧 PRD §2.2-c（散文）**

> 埋め込みが手書きルールに 163 USD 勝った（2,783 → 2,620）。
> シエンタでは起きなかった逆転が、複数車種では起きる。これが「機能A を作る意味」の実測値である。
> （中略）単一車種では互角、複数車種では人手のルールだけが落ちる。
> 機能A の価値は扱う対象の多様性しだいであり、1車種のデモでは価値が見えない。
> 製品デモや評価データは複数メーカーで用意することが要件になる。

**書き直し版（表の1行）**

> | E1 | 単一車種では人手の正規表現と埋め込みが互角、複数車種では人手ルールだけが落ちる | §6.1。デモ・評価データは複数メーカーで用意する |

結論は残っているが、**なぜそう言えるのかが消えている。**
「163 USD 勝った → シエンタでは起きなかった → だから多様性しだい → だから複数メーカーで」
という推論の鎖が、参照コードつきの1行に畳まれた。

検索と参照には強く、通読には向かない。**これが「LLM が読むことを前提にした文章」の正体。**
書き直し版と `decisions.md` は破棄し、PRD は 0.5 のまま据え置いた。

## 4. ついでに見つけたバグ

`scripts/check_docs.py` の **R 番号の検査が、書かれてから一度も動いていなかった。**
定義元を `related-work.md` に指定していたが、あのファイルに `R1`〜`R8` という記号は
1つも出てこない（あちらは論文の整理そのもので、番号を振っているのは PRD §3 の対比表）。
定義元が空だと検査をスキップする作りなので、無言で無効化されていた。
最終的に、P・S・R の3つとも**定義元を `docs/README.md` に一本化**して直した
（後述のとおり、書き換え後の PRD には P / S / R の表が無くなったため）。
検査の向きも変え、「日付つきドキュメントが使っている番号が `docs/README.md` に
定義されているか」を見るようにした。

## 5. 最終的にどうなったか

**PRD は人間の手で 733行から 153行に書き直された。**節番号は全廃され、
測定記録・検証計画（P）・受け入れ基準（S）・先行事例の対比（R）・未決事項（§7）・
リスク（§9）・マイルストーンは PRD から無くなった。
残ったのは「何を作るのか」だけである。2 で挙げた問題はこれで解消した。

旧 PRD の全文は git にある（`git show 93c1247:docs/PRD.md`）。

### これに伴って直したもの

- **P / S / R の定義元が `docs/README.md` に移った。**PRD から表が消えたため。
  約60箇所の日付つきドキュメントがこの記号を使っているので、定義自体は残す必要があった
- **旧節番号の対応表を `docs/README.md` §2 に置いた。**日付つきドキュメントは記録なので
  書き換えない方針であり、`PRD §8` `§7-1` のような参照はそのまま残る。読み替えで対応する
- **コード51箇所の PRD 参照を、節番号から節名に張り替えた。**
  `PRD §6.3` → `PRD「信頼度ルーティング」`、`PRD §2.2-g` → `docs/2026-08-29-denoise.md` など。
  節名なら次の改版でも壊れない
- **`unfold/feature.py` の利用者向けエラーメッセージ**が `PRD §7-1` を出していたので、
  節名に変えた。`tests/test_feature.py` の `match` も合わせた
- **`unfold/fallback.py` の説明が事実とズレていた。**「APIキーの入手経路が未確定なので
  まだ呼べない」と書いたままだったが、キーは 8/31 に入手し `ClaudeFallback` も実装済み
- **`scripts/check_docs.py`** — 記号検査を `docs/README.md` 基準に組み替え（§4）
- **`.claude/skills/update-docs/SKILL.md`** — 書き直しとは独立に成り立つ書式の決まりと、
  「PRD をこちらから全面的に書き直さない」という方針を残した
